# Zotero AI Reading

Release: **0.4.0**. The agent reads the MinerU Markdown, the scripts place its highlights on the PDF, write them to Zotero through its local API, and write an Obsidian note identical to what BibNotes's "Update Current Note" would make. Later the user works on the paper with their usual flow (edit in Zotero → "Add Note from Annotations" → Ctrl+P update); the note stays merge-safe. A paper read before, or with a note of the user's, can be added to (`--update`): new annotations go beside the existing ones and into the note's "Extracted Annotations" as a Ctrl+P update would put them, and the six fields gain marked, dated additions.

## Requirements

Windows; Zotero 10 running with the local API enabled (Settings → Advanced → "Allow other applications on this computer to communicate with Zotero"), its default annotation note templates and an English interface (the note is built as Zotero builds it; `note` stops otherwise); Python with `pymupdf`, `numpy`, `scikit-image`, `pillow`, `pyyaml`; Node.js; the Obsidian vault with BibNotes Formatter and the Better BibTeX JSON export it reads. `prepare` stops with the exact problem if the BibNotes set-up differs from the one the merge rules rely on; [references/setup.md](references/setup.md) explains that set-up and the Zotero/BibNotes behaviour behind every rule — read it when a check fails or before changing the scripts.

## Rules

- **Zotero is changed only by `write` and `undo`**, through the local API. Never delete permanently: `undo` moves the AI annotations to the Zotero trash; nothing uses the API's DELETE.
- **Write access** is the user's: the first `write` (and any after the key was cleared) shows Zotero's "Local API Authorization" dialog, and the command waits until the user answers. The user clicks **Always Allow**; the key is then kept in `%LOCALAPPDATA%\AI-Config\zotero-ai-reading\local-api-key.json` on that computer (never printed, never in OneDrive or the skill). Zotero → Settings → Advanced → "Clear Write Authorizations" revokes it.
- **Papers with annotations or a note** are skipped unless asked. `--update` adds to them, whoever wrote what is there (AI-tagged annotations, the user's annotations, an AI-draft note or the user's own note): use it when the user asks for papers to be read again or added to, and for a paper an earlier reading already covered when a new task uses it (the user's standing request of 2026-11-17: add the new task's points). `--alongside` (papers with only the user's annotations, no note) and `--replace-ai-draft` (an AI draft that 0.4.0 or later wrote and nobody changed since, whose AI annotations were undone) also only on request.
- **An existing note is only added to**, never rewritten: `note` inserts lines and checks that every line of the note is still there, unchanged and in order, front matter included; it keeps the old text as `note-before.md` in the run folder and stops if the note changed meanwhile. What the user deleted or changed in the note stays so.
- Batches of up to **10 papers** per run directory. Missing or stale Markdown: offer `mineru-api-batch-convert`, or `marker-api-batch-convert` when MinerU is unavailable (same output layout; its `marker-batch-convert` marker is checked against the PDF like MinerU's); do not read the PDF instead. "Untracked" Markdown (no converter marker, e.g. made before the markers existed) can be read as it is when it looks complete.
- PDFs, MinerU outputs and plugin settings are read, never edited; notes are written or added to only by `note`, as above.

## Workflow

Everything this skill needs is in its own folder, next to this file; a run needs nothing from other run folders, test records or development copies of the skill. Run all commands from this skill's `scripts/` folder with the project's Python (in the Paper Library: `& "$env:LOCALAPPDATA\AI-Config\bin\run-science.ps1" zotero_ai_reading.py ...` in PowerShell; from another shell `powershell.exe -NoProfile -ExecutionPolicy Bypass -File "<LOCALAPPDATA>\AI-Config\bin\run-science.ps1" zotero_ai_reading.py ...`). Never call a bare `python` on Windows: it may be the Microsoft Store stub, which hangs. Use one run directory per batch, always given explicitly: in the records of the research project the papers are read for, named `<YYYY-MM-DD>-<topic>`; ask the user when the project is unclear. The Paper Library itself keeps no run records.

1. **Prepare:** `prepare --library-root <Paper Library> --run-dir <run> --folder "<folder relative to the library root>"` (or `--citekey ...`); to add to papers read before or with a note, add `--update --task "<the research task or request>"` (the task labels every addition). It selects up to 10 ready papers, runs Windows OCR for scanned PDFs (also when the text layer is only a download stamp or unreadable, or is a publisher's OCR layer that does not lie on the printed words) and lists every skipped paper with its reason; with `--update` it shows what each paper has already and saves the annotations on its PDF in `<run>/<citekey>/existing-annotations.json`. Report skips to the user.
2. **Read:** for each ready paper, read its whole Markdown and write `<run>/<citekey>/reading.json` following [references/reading.md](references/reading.md): the user's colour meanings, verbatim quotes, comments, and the six fields as concise text with optional detail bullets. This is the agent's real work: judge what matters in this paper, be accurate, and annotate by importance, not to a count. `pagemap --run-dir <run>` lists the PDF page of every section, figure, table and numbered equation, for the `{p.N}` links in detail bullets. When adding to a paper (`--update`), first read its note (`note_path` in `batch.json`) and `existing-annotations.json`; `reading.json` then holds only what is new (reading.md, "Adding to a paper read before"). A reading written before 0.4.0, or for a new or replaced note, holds full fields: rewrite them as additions before `place` (it warns when all six are given); whether to add to a note or replace it is the user's decision.
   **Check each paper here:** `place --run-dir <run> --citekey <key ...>` is the check for `reading.json`; write no validator of your own. It reports reading problems and dropped items and draws `preview_p*.png` in the paper's folder (annotations already on the PDF in grey outline). Fix what it reports: for a dropped item pick another sentence (or the other half of one split by a page break) or another figure/equation, or delete it; an item dropped as a repeat of an existing annotation (or of an earlier item of the same reading) is already annotated, so put a new point about it into its comment or a field addition instead. Look at the paper's previews, first at the highlights it lists as snapped; a highlight on the wrong lines is worse than a dropped one. Repeat until nothing is dropped or misplaced, and report any item you had to give up. Its coverage line (annotations by colour, frames, pages covered, pages with no annotation) is for your own check, not a target; say in your report why a page with a section of its own has none. The first `place` of a paper can take minutes (figure search): give the command a timeout of at least 10 minutes.
   **In parallel:** papers are independent in this step. An agent that can run sub-agents in parallel may give each a share of the papers; each loads this skill, writes only its own papers' `reading.json` and runs `pagemap`/`place` only with `--citekey` for its own papers. Every other step runs once per batch, in order, in one agent.
3. **Place the batch:** `place --run-dir <run>` once. Papers already placed and checked in step 2 come back "unchanged"; only papers placed now (changed since, or never checked) need fixing and a preview check here, as in step 2. One agent working alone may skip the per-paper runs and do the whole check here. If you cannot view images, say so and ask the user to check the previews before step 4.
4. **Zotero:** `write --run-dir <run>`. It checks every paper again before changing anything (the same rules as `prepare`; with `--update`, no new annotation may repeat one made since), then writes the AI annotations (tag `AI`) and, for a paper getting its first note, the item tag `ai-draft` (a paper with a note keeps its tags). Before running it, tell the user that a Zotero dialog may appear and to click "Always Allow"; give the command a timeout of at least 10 minutes. A run writes once; `write` refuses a run that has already written, and `place` no longer changes a written paper. If the write is cut off (also when the command was stopped), it reads back what reached Zotero and says so: then `verify`, `undo`, and a new run directory; never `write` again. If nothing reached Zotero (access denied, local API off), fix that and run `write` again.
5. **Verify:** `verify --run-dir <run>` (read-only). Stop and report on any problem. Changed item fields can come from the user's Zotero plugins when they open the paper in the meantime (e.g. a tag rule on closing the tab); report them, they are not write errors.
6. **Notes:** `note --run-dir <run> --agent "<agent and model>"`. It builds the annotation note that Zotero's "Add Note from Annotations" would make (frame pictures rendered from the PDF), renders each note with the user's installed BibNotes, fills the six fields, checks YAML, that every AI annotation is linked and every frame has its picture, and that an immediate BibNotes re-update inserts nothing beyond BibNotes's known quirks (which it lists in the report), and only then writes the note and its pictures into the vault. For a paper with a note (`--update`) it adds instead: this run's annotations, in the lines BibNotes renders for them, go into "Extracted Annotations" in note order (each right before the next annotation the note already has, or at the end of that section), each field addition goes below that field's text as a bullet `AI 补充（<date> · <task>）`, and `ai_updates` in the front matter records date, task and agent; the same checks apply, plus that no line of the note was changed or removed and that a later Ctrl+P update finds every added line. A paper's `note` runs once per run directory. `--agent` names the agent and model that wrote `reading.json`, with the reasoning effort when known. If the reading was delegated, name the sub-agent that did it, not the one that delegated, e.g. "opencode document (gpt-6.1-sol, medium)" or "Codex (gpt-6.1-sol, high)".
7. **Report** from `<run>/report.md`: notes written or added to (as links), annotations placed and dropped (repeats of existing annotations separately), skipped papers, problems of the Markdown conversion you noticed (these belong here, not in the notes), and the user's remaining step: MarkDB-Connect → Sync Tags in Zotero.

**Undo** only on request: `undo --run-dir <run> [--citekey <key ...>]` moves the run's AI annotations (of those papers only, with `--citekey`) to the Zotero trash (restorable there) and removes the `ai-draft` tags it added; it leaves notes alone, so move a written note and its pictures out of the vault (do not delete them) if they should go; a note this run added to has its earlier text in `<run>/<citekey>/note-before.md`.

When the user takes a paper over, nothing special is needed: AI annotations can be edited, recoloured or deleted like their own; removing the `ai-draft` tag in Zotero removes it from the note at the next update.

## Recording Defects

When real use (not a test) shows a defect in this skill (a script error, a check that let a wrong result through, a result you had to correct or work around, a correction from the user, or instructions that proved wrong), write one note per defect to `%OneDrive%\AI-Config\Skills\feedback\zotero-ai-reading\<YYYY-MM-DD>-<slug>.md`: front matter `skill`, `version`, `date`, `reporter` (agent and model), `status: open`; then what happened, what was expected, evidence (command, input identifiers, a short output excerpt; paths relative to `%OneDrive%`), and the workaround. No credentials or long source text; never edit an existing note. Expected outcomes (documented skips, missing inputs, user decisions) are not defects. If `%OneDrive%\AI-Config\Skills` does not exist, skip this and say so. List written notes in the final report. Here that includes a highlight or frame in the wrong place that `place` did not report, an item dropped although its text is in the PDF, a `verify` or `note` check that missed a problem, or a BibNotes update that changed the note; problems of the Markdown conversion itself stay in the run report.
