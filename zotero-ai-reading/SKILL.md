# Zotero AI Reading

Release: **0.5.1**. The agent reads each paper's converted Markdown with a question; the scripts place its highlights and frames on the PDF, write them and the paper's content tags to Zotero through its local API, and write the Obsidian note that BibNotes's "Update Current Note" would make, or add to the paper's existing note. The user goes on with their usual flow (edit in Zotero → "Add Note from Annotations" → Ctrl+P update); the note stays merge-safe.

## Requirements

Windows; Zotero 10 running with the local API enabled (Settings → Advanced → "Allow other applications on this computer to communicate with Zotero"), its default annotation note templates and an English interface; Python with `pymupdf`, `numpy`, `scikit-image`, `pillow`, `pyyaml`; Node.js; the Obsidian vault with BibNotes Formatter and the Better BibTeX JSON export it reads. `prepare` stops with the exact problem if the set-up differs. [references/setup.md](references/setup.md) explains the set-up and the Zotero/BibNotes behaviour behind every rule and has a troubleshooting table: read it when a step fails or before changing the scripts.

## Rules

- **Zotero is changed only by `write` and `undo`**, through the local API. Nothing is deleted permanently: `undo` moves the AI annotations to the Zotero trash.
- **Write access** is the user's: the first `write` shows Zotero's "Local API Authorization" dialog and waits; the user clicks **Always Allow**. The key is kept in `%LOCALAPPDATA%\AI-Config\zotero-ai-reading\local-api-key.json` on that computer (never printed, never in OneDrive or the skill); Zotero → Settings → Advanced → "Clear Write Authorizations" revokes it.
- **Every run reads for a question** (`--task`): the user's question, or the research project's topic when the user named none; ask when it is unclear.
- **Papers read before** (annotated, AI or not, or with a note) are added to with `--update`, the user's standing request of 2026-11-17: a new question's points go into the papers read earlier. Without it they are skipped.
- **A paper's notes are found by its Zotero item**, in any vault folder: the note's "zotero entry" link decides, its file name `@citekey.md` only when that link is missing or names an item Zotero no longer has. A paper filed under several topics may have several notes; `--update` adds to each. A new note goes in the folder mirroring the PDF's.
- **An existing note is only added to:** `note` inserts lines and extends the `tags:` list; every other line stays as it is, front matter included. The old text is kept as `note-before.md` in the run folder (`note-before-2.md` for a second note).
- Batches of up to **10 papers** per run directory. Missing or stale Markdown: offer `mineru-api-batch-convert`, or `marker-api-batch-convert` when MinerU is unavailable; do not read the PDF instead. "Untracked" Markdown (no converter marker) can be read when it looks complete.
- PDFs, converted Markdown and plugin settings are read, never edited.

## Workflow

Run all commands from this skill's `scripts/` folder with the project's Python (in the Paper Library: `& "$env:LOCALAPPDATA\AI-Config\bin\run-science.ps1" zotero_ai_reading.py ...` in PowerShell; from another shell `powershell.exe -NoProfile -ExecutionPolicy Bypass -File "<LOCALAPPDATA>\AI-Config\bin\run-science.ps1" zotero_ai_reading.py ...`). Never call a bare `python` on Windows: it may be the Microsoft Store stub, which hangs. Everything a run needs is in this skill's folder. Use one run directory per batch, always given explicitly, in the records of the research project the papers are read for, named `<YYYY-MM-DD>-<topic>`; the Paper Library itself keeps no run records.

1. **Prepare:** `prepare --library-root <Paper Library> --run-dir <run> --task "<question>" --folder "<folder relative to the library root>"` (or `--citekey ...`), with `--update` to add to papers read before. It selects up to 10 ready papers, runs Windows OCR for scans, lists every skipped paper with its reason (report them to the user) and saves the annotations already on each PDF, in Zotero or stored in the file, in `<run>/<citekey>/existing-annotations.json`.
2. **Read and check each paper:** read its whole Markdown and write `<run>/<citekey>/reading.json` following [references/reading.md](references/reading.md). This is the agent's real work: judge what matters, be accurate. `pagemap --run-dir <run>` lists the PDF page of every section, figure, table and numbered equation, for `{p.N}` links. Then `place --run-dir <run> --citekey <key>` checks the reading (write no validator of your own): it reports problems and dropped items (repeats of annotations already there, items it cannot place) and draws `preview_p*.png` in the paper's folder, existing annotations in grey. Fix what it reports and look at the previews, first at the highlights it lists as snapped and at every frame: a highlight or frame in the wrong place is worse than a dropped one. Repeat until nothing is dropped or misplaced; report items you gave up. The first `place` of a paper can take minutes: allow at least 10 minutes.
   Papers are independent here: sub-agents may read them in parallel, each writing only its own papers' `reading.json` and running `pagemap`/`place` with `--citekey`. Every other step runs once per batch, in one agent.
3. **Place the batch:** `place --run-dir <run>` once; papers checked in step 2 come back "unchanged". If you cannot view images, say so and ask the user to check the previews before step 4.
4. **Zotero:** `write --run-dir <run>` (allow at least 10 minutes; tell the user a Zotero dialog may appear). It checks every paper again, then writes the AI annotations (tag `AI`), the reading's tags and, for a paper getting its first note, the tag `ai-draft`. A run writes once. If `write` reports a cut-off write, do not write again: `verify`, then `undo` and a new run directory; if it reports that nothing was written, fix the cause and run it again.
5. **Verify:** `verify --run-dir <run>` (read-only). Stop and report any problem. Changed item fields can come from the user's Zotero plugins while they have the paper open; report them, they are not write errors.
6. **Notes:** `note --run-dir <run> --agent "<agent and model, with reasoning effort>"`, naming the agent that wrote `reading.json` (for a delegated reading the sub-agent, e.g. "Codex (gpt-6.1-sol, high)"). It writes each new note as BibNotes renders it with the fields filled, or adds to the paper's note: this run's annotations into "Extracted Annotations" in note order, each field addition below its field as `AI 补充（<date> · <task>）`, the question to `ai_updates`, the new tags to `tags:`. It checks the note before writing it (links, pictures, YAML, a later Ctrl+P update stays clean) and runs once per paper and run directory.
7. **Report** from `<run>/report.md`: notes written or added to (as links), annotations placed and dropped, tags added, skipped papers, problems of the Markdown conversion you noticed (here, not in the notes), and the user's remaining step: MarkDB-Connect → Sync Tags in Zotero.

**Undo** only on request: `undo --run-dir <run> [--citekey <key ...>]` moves the run's AI annotations to the Zotero trash and removes the tags it added. Notes stay: move a written note and its pictures out of the vault (do not delete them) if they should go; a note the run added to has its earlier text in `<run>/<citekey>/note-before.md`. To read a paper again from scratch: undo it, move its note out, and use a new run directory.

When the user takes a paper over, nothing special is needed: AI annotations can be edited, recoloured or deleted like their own; removing the `ai-draft` tag in Zotero removes it from the note at the next update.

## Recording Defects

When real use (not a test) shows a defect in this skill (a script error, a check that let a wrong result through, a result you had to correct or work around, a correction from the user, or instructions that proved wrong), write one note per defect to `%OneDrive%\AI-Config\Skills\feedback\zotero-ai-reading\<YYYY-MM-DD>-<slug>.md`: front matter `skill`, `version`, `date`, `reporter` (agent and model), `status: open`; then what happened, what was expected, evidence (command, input identifiers, a short output excerpt; paths relative to `%OneDrive%`), and the workaround. No credentials or long source text; never edit an existing note. Expected outcomes (documented skips, missing inputs, user decisions) and problems of the Markdown conversion itself are not defects; a highlight or frame in the wrong place that `place` did not report, an item dropped although its text is in the PDF, or a check that missed a problem are. If `%OneDrive%\AI-Config\Skills` does not exist, skip this and say so. List written notes in the final report.
